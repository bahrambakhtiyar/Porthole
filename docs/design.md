# Using Porthole in detail

## Install in detail

Everything about installing that the README's short steps leave out.

### Linux

| Way | Status | How |
| --- | --- | --- |
| **Snap Store** | Coming soon | `sudo snap install porthole` |
| **Snap file** | On the [Releases page](https://github.com/bahrambakhtiyar/Porthole/releases) | `sudo snap install --dangerous ./porthole_0.1.0_amd64.snap`. Snap asks for `--dangerous` for any file that doesn't come from the store; it isn't a warning about Porthole. |
| **AppImage** | On the [Releases page](https://github.com/bahrambakhtiyar/Porthole/releases) | Download `Porthole-x86_64.AppImage`, make it executable (`chmod +x Porthole-x86_64.AppImage`) and run it. Nothing to install; it brings its own Python. |
| **.deb** (Ubuntu, Debian, Mint) | On the [Releases page](https://github.com/bahrambakhtiyar/Porthole/releases) | `sudo apt install ./porthole_0.1.0_all.deb`, then start **Porthole** from the app menu, or run `porthole`. |
| **APT repository** | Coming | Updates with the rest of the system. The one-line setup will be in [packaging/apt/README.md](../packaging/apt/README.md). |

The snap and the AppImage are for 64-bit Intel or AMD PCs (x86_64). On an ARM PC, such as a Raspberry Pi, use the .deb (it runs on the system's Python 3.10 or newer) or run from source.

The AppImage and the .deb open Porthole in its own window when Chrome, Edge, Chromium or Brave is installed. Closing that window stops Porthole (if more than one Porthole window is open, closing the last one does), and stopping Porthole closes it. That window can't see your browser's tabs: to share a tab or its sound, press **Open in my browser** on the page. Without one of those browsers, or if the window can't open, Porthole opens in a tab of your default browser.

**The Snap version opens Porthole in your default browser instead of its own window**, because a snap can't start the browsers installed on your PC. Stop it with **Quit** on the page. Recordings still go to your Videos folder.

### Windows, from source

A Windows installer comes later. Until then, run Porthole from source:

1. Install Python 3.10 or newer from [python.org](https://www.python.org/downloads/).
2. Download Porthole (on GitHub: **Code > Download ZIP**) and unzip it.
3. In that folder, run `py start.py` (see [Starting and stopping](#starting-and-stopping)). Windows Firewall asks whether to allow Python: allow it on both **Private** and **Public** networks.

`py start.py --install-launcher` adds Porthole to the Start menu (see [Launchers and the app menu](#launchers-and-the-app-menu)).

### macOS, from source

A Mac app comes later. Until then, run Porthole from source:

1. Install Python 3.10 or newer (from [python.org](https://www.python.org/downloads/), or Homebrew).
2. Download Porthole (on GitHub: **Code > Download ZIP**) and unzip it.
3. In Terminal, in that folder, run `python3 start.py` (see [Starting and stopping](#starting-and-stopping)).
4. If macOS asks to allow finding devices on your local network, click **Allow**. The easy address needs it.
5. The first time you share, macOS asks to allow screen recording, for your browser or for the app you started Porthole from (Terminal, say). Allow it in **System Settings > Privacy & Security > Screen & System Audio Recording** (on macOS 14 and older it's called **Screen Recording**), then quit the app it named and start Porthole again with `python3 start.py`.

Porthole opens in its own window when Chrome, Edge, Chromium or Brave is installed, or else in your default browser (Safari, say). That window is a separate copy of the browser. If the browser wasn't open already, clicking it in the Dock, a link in another app, or **Open in my browser** may open in Porthole's copy, without your bookmarks or sign-ins. When Porthole stops, it closes that copy only if nothing else is open in it. Stop Porthole with **Quit** on its page, by closing its window, or with Ctrl+C in Terminal. Recordings go to **Movies > Screen shares**.

## Starting and stopping

From the app menu or the Start menu: **Porthole** (see [Install in detail](#install-in-detail) and [Launchers and the app menu](#launchers-and-the-app-menu)). Or from a terminal:

```bash
python3 start.py
```

On Windows use `py start.py`. Needs Python 3.10 or newer and nothing else. To use it on another PC, copy Porthole's folder.

1. The sharer page (`http://127.0.0.1:8765/share`) opens in its own window when Chrome, Edge, Chromium or Brave is installed, or else in your default browser. Use `--browser-tab` to always get a browser tab.
2. Press **Start sharing** and pick a screen or a window. To share a browser tab or its sound, first press **Open in my browser** (Porthole's own window can't see your browser's tabs; the devices you let in or turned away and the switches go along), or start with `--browser-tab`.
3. Viewers scan the QR code or open the link on the page.
4. **Quit** on the sharer page, closing Porthole's own window, Ctrl+C in the terminal, or closing the terminal stops it. After **Open in my browser**, use **Quit**. The next run makes a new link; old links stop working.

Starting the same copy again while it's running just opens the sharer page, even when it runs on another port (see below). If the sharer page is already open in another window or tab, the new one says so ("Sharing is on in another window or tab." while that one shares, "Porthole is open in another window or tab." while it doesn't; its status line says "Sharing in another window or tab" or "Open in another window or tab", and it has no Watching list) and offers **Use this one**, so a stray click never cuts a live share. The page that takes over, even in another browser, starts with the devices let in or turned away and the switches of this run: Porthole keeps them while it runs.

If Porthole stops without a word (it crashed or was killed), the sharer page says "Porthole isn't running any more. You can close this page." and turns its buttons off. Start Porthole again for a new link. Once it runs again on the same port, an old page says "Porthole was restarted. Use its new page, or reload this one." (a phone or PC that was watching: "Porthole was restarted. Use its new link, or try again.").

Porthole uses port 8765 unless you pick one with `--port`. When 8765 is taken:

- by another copy of Porthole (another install: the snap, the .deb, an AppImage or another folder), that copy is stopped, even while it is sharing, and this one takes its place. The terminal says so: "Stopped the Porthole from /usr/share/porthole and started this one."
- by anything else, this one uses the next free port and says so: "Port 8765 is busy, so Porthole uses port 8766." A Porthole that doesn't answer is treated the same way. If another Porthole can't be stopped, the line names it instead: "Couldn't stop the Porthole from /usr/share/porthole, so this one uses port 8766." The link, the QR code and the easy address on the sharer page show the port in use. Settings saved on the sharer page (the theme and the switches) belong to one port, so on another port they start from the defaults.

With `--port`, Porthole stays on that port: a Porthole already there is opened, never stopped, and anything else there is an error whose message names the command to try another port with (`porthole` for the snap and the .deb, the AppImage's own file, `python3 start.py` from a folder).

If the PC moves to another Wi-Fi while Porthole runs, the link and QR code on the sharer page update within about 20 seconds. People already watching keep watching where the network allows it. With no network at all the page says "This PC has no network. Connect it to Wi-Fi or a network cable; the link shows here once it's connected." The link and the QR code then show by themselves, within about 20 seconds; no restart is needed (a restart would make a new link). The terminal says so too: "This PC has no network now, so other devices can't connect.", then `Back on the network. Viewers (phone or PC): <link> (same link as before)` when the address comes back as it was, or `The network address changed. Viewers (phone or PC): <link>` with the new link.

## The sharer page

One plain column, from top to bottom:

- **Header:** the name, an **Auto / Light / Dark** switch (Auto follows the system; remembered on this PC) and **Quit**.
- **Status:** Not sharing, Sharing, Sharing · recording, or Paused (on a page waiting while another one shares: Sharing in another window or tab, or Open in another window or tab).
- **Start sharing**, then a small preview of what viewers see and the buttons below.
- **Waiting devices** (with Ask on) right under the buttons, each with **Allow** and **Deny**.
- **Join:** the QR code, the easy address in large type when it is on, the link with **Copy**, and other addresses folded away.
- **Watching:** who is watching, with a short state (Watching, Weak signal, Waiting, Can't connect). Point at a device's name for its live numbers, e.g. `1280×720 · 30 fps · 4.1 Mbps`.
- **Settings:** the three switches.

| Control | What it does |
| --- | --- |
| **Pause / Resume** | Viewers see a plain "Paused" card instead of your screen and hear nothing, with a small "Paused" note at the top of their screen, also when they have zoomed in; devices that join meanwhile see both too. The preview shows the card as well. A recording pauses with you, so the paused part is left out of the file. |
| **Change** | Pick another screen, window or tab without dropping viewers. In Chrome and Edge, **Share this tab instead** on the browser's sharing bar switches to the tab you are looking at; viewers and the recording carry on. Porthole's own tab is left out of the list. Tabs need the page in your browser, not in Porthole's own window. If what you pick can't be shared, the page says "Couldn't change what's shared: …" and the current share goes on. |
| **Record / Stop recording** | Records what you share (with sound if shared) into `Videos/Screen shares/` (`Movies/Screen shares/` on a Mac) as MP4 (H.264) or WebM. It is saved piece by piece, so long recordings don't fill memory and a crash keeps what was recorded. **Open folder** shows the file (if the folder can't be opened, the page says where the recording is; on Linux, opening folders needs xdg-utils). **Change** continues in a new file. If the sharer page closes and doesn't come back within 10 seconds, the file is finished with what was saved. If the disk fills up (or can't be written to), the recording stops and keeps everything until then: "The recording stopped: the disk is full. What was recorded until then is saved." A recording started while paused and stopped before **Resume** has nothing in it: the page says "Nothing was recorded." and leaves no file. After **Change** while paused, the part before **Change** stays saved and shows, with **Open folder**. |
| **Stop sharing** | Ends the share; viewers wait for the next one. |
| **Mini controls** | Chrome and Edge: a small window that stays on top of other windows, with the status, **Pause / Resume**, **Stop sharing**, and **Allow / Deny** for the first waiting device. Hidden in other browsers. |
| **Ask before someone watches** | On by default. New devices wait until you press **Allow** (or **Deny**; **Deny all** appears when two or more wait). Each waiting device shows a 3-digit code ("Your code: 482") that also appears in its row, with the time it joined, so you can tell which phone is which; devices of the same kind are numbered ("Android phone 2"). While the page is in the background you get one notification ("2 waiting") and a count in the tab title; the browser asks once whether Porthole may show notifications, when you press **Start sharing** (or turn Ask on), and never again after a no. A device that reconnects during the same run (a locked phone, a Wi-Fi drop) keeps its row, name and code, and stays allowed. An approval is for the device's browser and the address it was allowed from: a phone that comes back with a new address is asked again (a denied one stays denied). A reloaded page keeps its row: Porthole keeps a closed page's row for 2 seconds, so the page is back in it, with its code. |
| **Remove** | Sends a viewer away. With "Ask before someone watches" on, they stay out for the rest of the run. |
| **Smooth motion** | Off: sharp text (30 fps, keeps resolution). On: up to 60 fps for videos and games, lowers resolution first when the network is tight. |
| **Easy address** | People on the same Wi-Fi can type a short name instead of the link. See [The easy address](#the-easy-address). |

The switches are remembered on this PC, by each browser. While Porthole runs it keeps them too, with the devices let in or turned away, for the page that takes over (**Open in my browser**, **Use this one**), which uses them for that run instead of what its own browser saved. A switch you change there is saved in that browser on its own. When you share a whole screen, the page reminds you that viewers can see your notifications: turn on Do not disturb, or share a window instead. When a device is turned away for opening too many tabs or trying too often, a line under Watching says so, e.g. "An Android phone couldn't join: too many tabs (14:05)".

Everything works with the keyboard alone. Screen readers hear the status, each device that starts waiting (once, with its code), and notes and errors as they appear. Both themes meet WCAG 2.2 AA contrast; see [Accessibility](#accessibility-23-nov-2026) below.

## Command-line options

| Option | What it does |
| --- | --- |
| `--port 8766` | Use this port (default 8765). Porthole then never moves to another port: if something else has it, Porthole stops with a message. |
| `--host 192.168.1.20` | Put this IPv4 address in the viewer link if the guessed one is wrong. |
| `--record-dir PATH` | Save recordings somewhere else. |
| `--no-browser` | Don't open the sharer page automatically. |
| `--browser-tab` | Open the sharer page in a tab of your default browser instead of its own window, so you can share a browser tab or its sound. Closing the tab doesn't stop Porthole; use **Quit**. |
| `--name office` | Use `office.local` as the easy address (default `porthole`). |
| `--no-discovery` | Turn the easy address off for this run. |
| `--verbose` | Print each request in the terminal (time, device address, method, path, status), with the room code shown as `****`. For finding out why a device can't connect. |
| `--install-launcher` / `--uninstall-launcher` | Add or remove the app-menu entry. |

## The easy address

Instead of the long link, people on the same Wi-Fi can type a short name.

1. Turn on **Easy address** on the sharer page (it is on unless you turned it off).
2. Viewers type `porthole.local:8765` in their browser. When Porthole runs on Windows or a Mac, plain `porthole.local` works too. The sharer page shows the address to type.

- Works on iPhone, Mac, Windows and Linux. Some Android phones can't open these names; they use the QR code.
- Turning it on also turns on **Ask before someone watches**, since anyone on the Wi-Fi can find it. Turning Ask off turns Easy address off.
- Turning it off (or turning Ask off) stops new visitors only. Devices already watching by the name keep watching, and can reconnect and get the next share, until they have been away for about two minutes (they closed the page, or the phone was locked or off the Wi-Fi that long); once the last of them has, the name stops working. Any other device that types the name meanwhile is told to use the link or the QR code, so nobody new joins by the name without **Ask**.
- The address only opens the share while you are sharing. Anyone who types it before you start sees a waiting page that opens the share once you start. If another device already uses the name, Porthole picks `porthole-2.local`.
- While it is on, a link or home-screen icon from an earlier run opens the current share instead of "This link doesn't work". With it off, old links don't work.

## Watching

- **Phones and tablets:** Android Chrome, iPhone/iPad Safari. **PCs:** any modern browser.
- **Buttons** appear along the bottom when you tap the picture (or move the mouse, or press Tab) and disappear completely after 3 seconds, so a tap on the picture never presses one by accident. The tap that brings them back doesn't press one either. They stay clear of the notch.
  - **Sound** (when sound is shared): the picture starts muted (browser rule); this turns sound on and off.
  - **Fit** (when zoomed) goes back to the whole picture.
  - **1:1** shows one picture pixel per screen pixel, for small text; press it again to fit. Hidden when the whole picture already shows every pixel.
  - **Pop out** puts the picture in a small window on top of other apps, where the browser supports it.
  - **Save** saves the current picture as `Porthole 2026-11-22 14-05-03.png`.
  - **Quality menu:** **Auto** adapts to the network, **High** keeps full quality, **Data saver** uses about 1 Mbps. Remembered on the device.
  - **Full screen** appears once the picture plays.
- **Zoom:** pinch to zoom (up to 5×), drag to move around, double-tap to zoom in or back out. On a PC, the mouse wheel zooms and dragging moves; with the keyboard, **+** and **-** zoom and the arrow keys move around a zoomed picture.
- **States:** Waiting, Connecting, Can't connect and Ended; a **Weak signal** badge appears when the picture is struggling, and a **Paused** note while the sharer has paused. The ended screen has **Try again**; after Porthole was restarted it says so ("Porthole was restarted. Use its new link, or try again."). These screens follow the device's light or dark setting; the picture area is always black. Screen readers hear each state, the waiting code, Watching once the picture plays, and Paused while the sharer has paused.
- **Home screen:** "Add to Home Screen" (Safari's share menu, or Chrome's menu) adds a Porthole icon that opens full screen. It opens the share it was added from; with Easy address on, it opens whatever is being shared, even after Porthole restarts.
- Phones can watch but can't share: mobile browsers don't allow screen capture.

## Network quality

Each viewer is adapted separately, so a weak phone doesn't lower quality for the others. On top of WebRTC's own bitrate control, the sharer checks each connection every 2 s and moves between full quality (8 Mbps), ¾ resolution (4 Mbps), ½ resolution (2 Mbps) and data saver (1 Mbps): two bad checks step down, five clean ones step back up. After a network blip it first repairs the existing connection (ICE restart), and only builds a new one if that fails.

## Sound

- **Chrome/Edge on Linux:** only a browser tab's sound. Pick the tab and turn on "Also share tab audio". In Porthole's own window, press **Open in my browser** first.
- **Chrome/Edge on Windows:** the whole computer's sound when sharing a screen ("Also share system audio"), also in Porthole's own window; a tab's sound with "Also share tab audio".
- **Chrome/Edge on a Mac:** a browser tab's sound ("Also share tab audio"). In Porthole's own window, press **Open in my browser** first.
- **Firefox and Safari:** no sound.

When nothing can be heard, the page says what this browser offers here: "No sound is shared. Use Change, pick a tab and turn on "Also share tab audio"." in Chrome on Linux, "No sound is shared. This browser can't share sound." in Firefox and Safari.

## Launchers and the app menu

```bash
python3 start.py --install-launcher
```

- **Linux:** adds Porthole to the app menu (`~/.local/share/applications`). From the AppImage, run `./Porthole-x86_64.AppImage --install-launcher`; the menu entry then starts that AppImage file, so keep it where it is.
- **Snap and .deb:** they come with their menu entry; `--install-launcher` isn't needed and just says so. If you added a menu entry earlier from the AppImage or a folder, it has the same name as the .deb's and hides it: `porthole --install-launcher` (or `--uninstall-launcher`) removes that older entry and says "Removed an older Porthole menu entry; the package's own entry stays."
- **Windows** (`py start.py --install-launcher`): adds it to the Start menu and the desktop. It runs without a console window.
- **Mac:** there is no launcher to add; `--install-launcher` just says so.

Started from a launcher there's no terminal, so use **Quit** on the sharer page (or close Porthole's own window) to stop it; start-up problems, and another Porthole being stopped to make room, show as a desktop notification (Linux) or a message box (Windows). The same goes for the AppImage started with a double-click. Remove with `--uninstall-launcher`.

## If viewers can't connect

- **Quick check.** On the phone, open `http://<the PC's address>:8765/` (the address and port are in the link on the sharer page; the port is another one if 8765 was busy). Any Porthole page, even "Nothing here", means the phone can reach the PC. If nothing loads, it's the network or the firewall.
- **Same network?** The phone must be on the same Wi-Fi as this PC, not mobile data and not a guest network. Guest networks and some office Wi-Fi block devices from seeing each other.
- **Wi-Fi that blocks devices (guest or office):** connect the PC and the viewers to a phone's hotspot instead. The video stays between the devices and uses no mobile data.
- **Windows firewall.** Allow Python when Windows asks, on both **Private** and **Public** networks (a Wi-Fi that Windows calls "public" needs the **Public** tick). If you once said no, or it still doesn't work, open "Allow an app through Windows Firewall" and remove the old `python` and `pythonw` entries, then start Porthole again and allow it. Started from the launcher it runs as `pythonw.exe`, which Windows asks about separately.
- **Ubuntu firewall.** With the firewall on, open the port once: `sudo ufw allow 8765/tcp` (the terminal names the port in use if 8765 was busy).
- **Mac firewall.** It is off unless you turned it on. If macOS asks whether Python may accept incoming network connections, click **Allow**. To change an earlier answer: **System Settings > Network > Firewall > Options**.
- **iPhone, iPad or Mac with any browser other than Safari:** allow **Local Network** for that browser in Settings (Privacy & Security > Local Network). Safari doesn't need this. Sharing from a Mac with macOS 15 or newer, allow the app you started Porthole from (Terminal, say) there too.
- **Easy address on a Mac says it couldn't start** just after you allowed Local Network access: turn **Easy address** off and on again. macOS turns down the first try while it asks.
- **Wrong address in the link.** If the PC has several networks, restart with `--host <the PC's Wi-Fi address>`.
- **A VPN** that sends all traffic through its tunnel can block local connections; pause it while sharing.
- **"This link doesn't work"**: the link is from an earlier run of Porthole, or has a typo. Check it against the link on the sharing PC, or scan the QR code. **"Porthole was restarted"** means just that: use the new link or QR code.
- **"Use the link"** means the phone opened Porthole by a name it doesn't answer to: another name for the PC (say `mypc.local:8765`), or the easy address after it was turned off. Open the link or scan the QR code instead.
- **"Too many Porthole tabs are open on this device"** or **"Too many tries"**: one device can have at most 5 viewer tabs open and start at most 6 new ones a minute. Close a tab, or wait a minute, then press **Try again**. The sharer page shows a line about it too.
- **Still stuck?** Start Porthole with `--verbose`. Each request shows in the terminal; if the phone's requests never show up, the network or a firewall is blocking it.

## Limits

- Made for a handful of viewers (at most 5 open tabs and 6 new connections a minute per device). Each viewer gets its own stream from this PC.
- Share from the PC that runs `start.py`: browsers only allow screen capture on `localhost`.
- No remote control (browsers can't control a PC). Phones may dim during long shares: keeping the screen awake needs HTTPS, which this doesn't use.

## How it works

`start.py` runs a small web server (Python standard library only). It serves the two pages and passes the short WebRTC set-up messages between the sharer and each viewer: Server-Sent Events from server to browser, `POST /signal` back, in order. The video never goes through the server.

- Each run gets a random room code; the viewer page and every message need it.
- The sharer page and its actions (quit, recording, open folder) only work from this PC, from the page itself: other devices and other websites are refused.
- Browsers hide their local address behind `xxxx.local` names that some routers can't resolve, so the server also forwards each network candidate with the real address it saw.

| --- | --- |

| `porthole/launcher.py` | Linux desktop entry and Windows shortcuts (none on a Mac) |

# Design history: version 1 (21 Nov 2026)

Version 1 approved and built on 21 Nov 2026, under the working name "LAN screen share". Version 2 approved 21 Nov 2026 (section below). Everything from here on is the design history; [Using Porthole in detail](#using-porthole-in-detail) above describes Porthole as it is now.

## Why

The goal is to show a PC's screen to phones and other PCs on the same local network. The people watching only open a link in their browser and install nothing.

## Goals

- The sharer uses a desktop browser (Chrome, Edge or Firefox) on the PC that runs the script.
- Viewers use any modern browser on a phone (Android Chrome, iPhone Safari) or a PC. They open a link or scan a QR code.
- Several viewers can watch at once.
- Video stays on the local network. It works with no internet connection.
- Sound is shared where the browser can capture it. On Linux Chrome that means one tab's sound; on Windows Chrome, the whole system's sound.

## Non-goals (not in this version)

- Remote control, recording, chat, or annotations.
- Sharing over the internet, or between different networks.
- Sharing from a phone. Mobile browsers can't capture the screen.
- Sharing from a PC other than the one running the script. That would need HTTPS and a certificate warning.
- Large audiences. Each viewer gets their own stream from the sharer's PC, which is fine for a handful of devices but not for dozens.

## Anti-goals (would count as failure even if it technically works)

- A viewer has to install something or click through a certificate warning.
- Anyone on the same Wi-Fi can watch without the link.

## Constraints

- Browsers allow screen capture only on secure pages, so the sharer opens the page as `http://localhost`. Viewers use the PC's network address. Plain HTTP is fine for watching.
- Python standard library only. Nothing to `pip install`, and Python is preinstalled on Ubuntu.
- Mobile browsers only autoplay video that is muted. The viewer page starts muted and offers "Tap to unmute". iPhone needs `playsinline`.
- Port 8765 by default, so it doesn't clash with common development servers on 8000 and 5173. It can be changed with `--port`.

## Approaches considered

| Approach | Trade-off | Verdict |
| --- | --- | --- |
| **Python script, standard library only** | Already installed on Ubuntu; nothing to download. A Windows PC needs Python installed once. | **Chosen** |
| Node script, no packages | Same design. Node doesn't come with a fresh Ubuntu, so it adds nothing over Python. | Dropped |
| Ready-to-run program (Go) for Windows and Linux | Double-click on any PC, but needs a Go toolchain to build and means rebuilding two files after every change. | Dropped |
| No server, copy-paste connection codes | Long text blocks to paste on every device for every viewer. | Ruled out |
| Public internet relay | Needs the internet and sends connection details off the network. | Ruled out |

## Design

**Running it.** `python3 share.py` prints the viewer link and opens the sharer page in the default browser. Ctrl+C stops it. The folder holds the script and the web pages; to use it on another PC, copy the folder.

**Server (only connects browsers, never touches the video).**
- Built on `http.server.ThreadingHTTPServer`.
- The sharer page is served only to requests from the PC itself (127.0.0.1 / ::1), so a viewer can't take the sharer's role.
- A random room code is created on each run. The viewer page and every connection message need it. A new run means a new link.
- Browsers exchange connection messages (join, offer, answer, network candidates, leave, sharing stopped) through Server-Sent Events (server → browser) and `POST` requests (browser → server). The server forwards each message between the sharer and one viewer, identified by a viewer id.
- **Phone connection fix.** Browsers hide their real address behind `xxxx.local` names, which some routers fail to resolve. Every candidate is forwarded unchanged. The server also forwards a copy with the real address: the viewer's IP as the server sees it, or the PC's IP on that viewer's network. Phones still connect when the Wi-Fi blocks those names.
- The QR code for the link is generated by the script itself, with no downloads or outside libraries.

**Sharer page.**
- Buttons: **Start sharing**, **Change what's shared**, **Stop**.
- Shows the viewer link with a copy button, the QR code, and the viewers connected right now (count and device type).
- One WebRTC connection per viewer. A viewer who opens the link before sharing starts waits, and gets the picture as soon as sharing starts.
- Quality is tuned for sharp text: the track hint is set to "detail", up to 30 frames a second, and a high bitrate, since the local network is fast.

**Viewer page.**
- The video fills the window. Tap for full screen, and tap to unmute when there is sound.
- Clear states: "Waiting for the screen…", "Connecting…", "Sharing stopped".
- Reconnects on its own after a dropped connection or a locked phone, and when the sharer restarts sharing. (Since 26 Nov 2026 it keeps its row on the sharer page: see the end.)

**Interface language.** English, easy to translate later.

## Testing

- Python `unittest` for message forwarding, the room-code check, the localhost-only sharer page, the candidate fix, and the QR generator. The QR output is checked with a decoder installed only in a throwaway test folder.
- Browser test: the sharer page has a test mode that sends a moving test picture instead of the screen. A browser opens it and a viewer tab on the PC's network address, and the test checks that frames arrive.
- Real check, by hand: share the actual screen and watch it on a phone.
- Firewall: if Ubuntu's firewall (ufw) is on, viewers need port 8765 opened with `sudo ufw allow 8765/tcp`. The script prints this hint.
- A VPN on the sharing PC can block local connections; the README tells people to pause it if viewers can't connect.

## Left to the builder

File layout inside the folder, the exact message format, reconnect timings, and the page styling (simple, clean, works on a phone screen).

# Version 2 (approved 21 Nov 2026)

Version 2 adds every idea from version 1's list of next steps (approval, recording, smooth mode, network adaptation, pinch-zoom and pan, desktop launchers for Linux and Windows), each switchable where that makes sense, plus more ways to cope with network quality. The code-review minors from version 1 are folded in as hardening.

## Sharer page

- **Ask before someone watches** (switch, off by default, remembered on this PC). New viewers see "Waiting for the sharer to let you in…"; the sharer gets **Allow / Deny**, a browser notification when the page is hidden (permission asked when Start sharing is pressed too, since 24 Nov 2026: see the end), and a count in the tab title. A device that reconnects during the same run keeps its approval (a random device token stored on the phone), and since 26 Nov 2026 its row (see the end). Turning the switch on approves everyone already watching; turning it off lets everyone waiting in.
- **Remove** next to every viewer. Removed and denied devices stay out for the rest of the run (until the switch is off and they reload).
- **Smooth motion** (switch, remembered): off = sharp text (track hint "detail", 30 fps, keep resolution); on = hint "motion", up to 60 fps, keep frame rate. Applies live while sharing.
- **Record / Stop recording.** The browser records the shared stream (MediaRecorder, MP4 where Chrome supports it, else WebM, 4 Mbps) and uploads it to share.py every 2 s; share.py appends to `<Videos>/Screen shares/Screen share YYYY-MM-DD HH-MM-SS.<ext>`. Long recordings never sit in browser memory and a crash keeps what was recorded. Changing what's shared closes the file and continues in a new one. Stopping sharing stops recording. After saving: file name and **Open folder**.
- **Quit** button (needed when started from a launcher with no terminal). Asks first if anyone is watching or a recording runs.

## Network adaptation (each viewer separately)

- WebRTC's own congestion control keeps working. On top, every 2 s the sharer reads each connection's stats (packet loss, round-trip time, available bandwidth) and moves between levels: full (8 Mbps), ¾ resolution (4 Mbps), ½ resolution (2 Mbps), data saver (½ resolution, 1 Mbps). Two bad samples in a row step down; five clean samples step up; 6 s pause after any change.
- Viewer menu **Auto / High / Data saver** (remembered on the phone). High pins full level, Data saver pins the lowest; Auto adapts.
- Sharer sees each viewer's live quality ("1280×720 · 30 fps · 4.1 Mbps"), marked when weak; the viewer sees a "Weak connection" badge from its own receive stats.
- Recovery: the sharer first tries an ICE restart on the same connection (after 3 s disconnected, or on failure); if that doesn't reconnect within 10 s it builds a new connection. Viewers keep asking with backoff as a last resort.
- Messages are sent in order, and each answer names the offer it answers, so a late answer can't break a newer connection.

## Viewer page

- **Pinch-zoom** up to 5×, one-finger pan, double-tap toggles 2.5× at that point and back to fit, **Fit** button when zoomed. Mouse wheel zooms and dragging pans on PCs. Tapping no longer toggles full screen (the **Full screen** button does); a tap shows the buttons.
- If the browser refuses to start playback, a "Tap to play" prompt appears.

## Launchers

- `share.py --install-launcher` adds "LAN Screen Share" with an icon: Linux to `~/.local/share/applications`; Windows to the Start menu and the desktop (PowerShell shortcut, `pythonw.exe` so no console window). `--uninstall-launcher` removes them.
- Starting it again while it runs opens the sharer page instead of failing ("Already running").
- Launched with no terminal (`--launcher`), start-up errors show as a desktop notification (Linux `notify-send`) or a message box (Windows).
- Windows can't be tested on this PC; its parts are built carefully and stay unverified until tried on Windows.

## Hardening (from the version 1 review)

- Local-only actions (quit, recording, open folder) need a same-origin `Origin` header, so other websites can't trigger them; the sharer page can't be framed (`frame-ancestors 'none'`) and refuses cross-site loads; `/signal` refuses a sharer id from another device.
- Request timeouts, an event-stream close check that works with many sockets, at most 5 viewer connections per device address, TCP keep-alive so vanished phones leave the list within about half a minute.
- Odd JSON (`{"type": []}`, deep nesting) gets a 400 instead of a crash.
- `--port` range-checked, `--host` must be an IPv4 address, friendly messages for reserved or protected ports, Windows hints say `py share.py`, the no-sound hint mentions Windows "Also share system audio" (since 24 Nov 2026 it fits the browser and system: see the end).

## Not in version 2

Remote control and keeping the phone screen awake (both impossible browser-only over HTTP), sharing from another PC, more than a handful of viewers.

# Version 3: easy address (approved 21 Nov 2026)

Version 3 adds a way for everyone on the network to find the share more easily. One PC shares at a time. Browsers can't search the network, so "discovery" means a short name people can type instead of a long random link.

- **Name announced by share.py itself** (chosen over relying on the system's announcer or the PC's own long name): a small built-in mDNS responder answers queries for `screen.local` (`--name` changes it) with this PC's Wi-Fi address only, alongside any system responder. If another device already answers for the name, it uses `screen-2.local`, `screen-3.local`, … It announces at start and withdraws the name when share.py stops.
- **Typing the easy address opens the viewer page** (`/` redirects to the current room) while Easy address is on; with it off, `/` stays a dead end for other devices as before.
- **Easy address switch** on the sharer page, on by default and remembered. Because anyone on the Wi-Fi can now find the page, **Ask before someone watches** is on by default too, and switching Easy address on also switches Ask on (Ask can still be turned off by hand).
- The sharer page shows the easy address in large type. The QR code keeps the numeric link, which works on every phone (some Android phones can't resolve `.local` names).
- **Port 80 where the system allows it**, so plain `screen.local` works: share.py also listens on port 80 and redirects to the main port. Windows usually allows it; Ubuntu needs a one-time setting (`sudo sysctl -w net.ipv4.ip_unprivileged_port_start=80`, documented). If port 80 isn't available, the address is `screen.local:8765`.
- The Host check also accepts the announced name (only that name).
- Not verifiable here: Windows (its own responder may hold port 5353 exclusively; then the page says the easy address isn't available), phones that resolve `.local`.

**Changed 22 Nov 2026** (version 4, P2; these replace the matching points above):
- The port 80 helper runs only on Windows and macOS. Linux shows `porthole.local:8765`; the `sysctl` setting is no longer suggested.
- The name is announced only when the sharer page asks (`POST /api/discovery`); Porthole never announces it at start. `--no-discovery` turns it off for the run.
- `/` redirects to the room only while the easy address is on and something is being shared (the page reports this with `POST /api/status`). The `.local` name reaches only the viewer page, static files, viewer events and `/signal`, never `/share` or `/api/*`. While the easy address is on but nothing is shared yet, `/` gives other devices a short "Nothing shared yet" page (503, no room code) that reloads itself every 5 s, because the sharer page shows the address before Start sharing; with the easy address off it stays the "Nothing here" dead end.
- Easy address on turns Ask on; Ask off turns Easy address off. Settings saved before the easy address existed load with Ask on. (Since 24 Nov 2026 off stops new visitors only: see "Visible changes (24 Nov 2026)" at the end.)
- The default name is `porthole` (`porthole.local`), not `screen`.

# Version 4, P3: fix list

These replace the matching points above.

- **Live addresses.** Porthole re-reads the PC's addresses every 10 s (not with `--host`). `/api/info` builds the links and the QR code from the current addresses, the sharer page re-reads it every 10 s and redraws them, and the easy address moves to the new first address (goodbye, then announce). The terminal prints the new full viewer link (since 26 Nov 2026 it says when the network goes, and "Back on the network" when it comes back with the same link: see the end). The room stays the same, so connected viewers are not dropped.
- **Liveness.** Keep-alives are data events (`{"type":"ping"}`) every 15 s. The viewer opens a new event stream after 40 s with no message at all, or when a POST answers 404 "unknown peer". The sharer page only does the latter: reopening its own stream could race its old connection and look like "sharing in another tab".
- **Check codes.** Each viewer connection gets a 3-digit code (100–999, unique among current viewers), shown on its waiting screen and on the sharer's row with the join time. The hub records the join time (`joined`, epoch ms, in `viewer-joined` and the sharer's `hello` list), so a sharer page reload keeps it. Rows of the same device kind are numbered ("Android phone 2").
- **Waiting viewers.** One notification ("N waiting", tag `porthole-waiting`) is updated as the count changes and closed when nobody waits. **Deny all** appears when two or more wait.
- **Limits.** Per device address: at most 5 open viewer connections and at most 6 new ones in 60 s. Browsers open at most 6 connections to one address and each viewer tab's event stream holds one, so with 6 tabs nothing else would get through; at 5, a 6th tab still loads and hears why it can't join. A refused viewer gets an event stream with one `{"type":"refused","reason":"too-many-tabs"|"too-many-tries"}` event, sees why, and stops retrying.
- **Recording.** Key frames every 2 s (`videoKeyFrameIntervalDuration`). An open recording is closed when the sharer page that started it goes away and isn't back within 10 s. A page is known by a random token it sends with its event stream and its recording (`page`): after a blip it comes back with the same one; a reloaded or new page has a new one and can't finish the old recording, so it doesn't keep it open.
- **Whole screen.** When a whole screen is shared, the sharer page says viewers can see notifications.
- **Answer retry.** A viewer whose answer fails to send tries once more after 2 s, if that connection is still current.
- **Linux addresses.** Interfaces that are down or point-to-point are skipped (SIOCGIFFLAGS).
- **Already running.** `/api/ping` reports the folder Porthole runs from. Starting a second copy from another folder says "Porthole is already running from <folder>. Opened it." The sharer page opens before the message, because a launcher's message box waits for OK; on Windows it shows as a notice, not an error. (Since 23 Nov 2026 that holds only with `--port`; without it another copy is stopped, see "Start-up: a busy port".)
- **Browser tests.** `tests/browser/run.mjs` drives headless Chrome over the DevTools protocol from Node (no packages); `tests/test_browser.py` runs it, skipped without Chrome or Node 22+ unless `REQUIRE_BROWSER=1`.

# Version 4, P4: redesign and new features

The aim: a clean look with dark and light modes and nothing that reads like a generated template. These replace the matching points above.

**Look (both pages).**
- One column, at most 680 px wide, 16 px side margins. Sections are separated by space and a thin line; no cards, shadows, gradients, emoji or decorative symbols (the header's ring, which is the logo, and the status dots drawn in CSS are the only marks).
- System font, 16 px text, headings 20 and 28 px, two weights (400 and 600), tabular figures for times and sizes, sentence case.
- Neutral greys and one blue accent. Green only for live, amber only for a weak signal, red only for errors. Both themes meet WCAG AA contrast; focus rings are visible.
- **Logo: the ring** (23 Nov 2026). The header's mark, a 22 px circle with a 5 px border in the accent colour, is Porthole's logo. Every app icon is that ring in white on a blue rounded tile, and nothing else: in the icon's 64 × 64 units the ring is 37.4 wide (58 % of the tile) and 8.5 thick (5/22 of its width, as the mark's border), and the tile is #2563eb with corners of radius 14. That blue is the icons' blue from before, a touch lighter than the light theme's accent (#2557d6); white on it is 5.17:1. `tools/make_icons.py` draws every file from these numbers: `web/icon.svg` (the browser tab, and the title bar of the app window), `assets/icon.png` (256 px) and its copy `snap/gui/porthole.png`, `assets/icon.ico` (16, 32, 48 and 256 px) and the home-screen icons. Edges are smoothed by how much of each pixel a shape covers, so the ring reads clearly at 16 px too. iPhone's home-screen icon (`web/icon-180.png`) fills its whole square and has no transparency, since iPhone rounds the corners itself and shows transparent parts as black; the manifest's icons aren't marked maskable, so they keep the rounded tile with clear corners, like the menu icons. `tests/test_icons.py` reads every file back and checks it against the mark in `style.css`: the ring's size and thickness, white only on the ring, the tile blue everywhere else, the corners, smooth edges, and an SVG of just the tile and the ring. Before, every icon showed a monitor with Wi-Fi waves, from before the rename. The pages ask for the icons by an address that names the ring (`/static/icon.svg?v=ring`, and the same `?v=ring` on the home-screen icons and the manifest): browsers keep a page's icon in a store of their own, apart from the HTTP cache, looked up by its address, so Porthole's own window kept the old picture in its title bar (seen on a real Ubuntu, 26 Nov 2026). A test pins `web/icon.svg`'s hash, so a new picture fails it until the address changes too. Porthole's desktop notices on Linux carry the ring as well (`notify-send -i` with `web/icon-512.png`).
- Buttons are 40 px high with 8 px corners: the main action filled blue, the rest outlined, **Quit** a quiet text button. **Stop sharing** is an ordinary button, and normal endings (quit, moved to another tab) are plain notes, not errors.
- Short labels, no tech words. Only Ask and Easy address keep a one-line explanation.
- **Theme:** Auto / Light / Dark in the sharer header, remembered in `localStorage` (`porthole-theme`) and set as `data-theme` on `<html>`; the colours are CSS variables for light, `[data-theme="dark"]`, and the system dark setting under Auto. `web/theme.js` holds the logic. The viewer page always follows the system for its waiting and ended screens; the picture area is black.

**Sharer page.** Header (mark, name, theme switch, Quit); a status line (Not sharing, Sharing, Sharing · recording, Paused; on a page waiting while another one shares, since 26 Nov 2026, "Sharing in another window or tab" or "Open in another window or tab": see the end) announced to screen readers, and written only when it changes so the same words aren't read out again; **Start sharing**, then a preview (at most 320 px wide) that shows what viewers see, and Pause, Change, Record, Stop sharing, Mini controls; waiting devices pinned under that with Allow, Deny and Deny all; Join (QR code about 160 px next to the easy address in large type, the link with Copy, other addresses folded); Watching (short states; the live numbers are in each row's tooltip); Settings. The element ids stayed, so the tests still find everything.

**Viewer page.** The idle button bar is hidden (`visibility: hidden`) after 3 s, not just faded, so a tap can't press an invisible button; any tap or mouse move shows it. On touch the browser picks the click target when the finger lifts, after the bar is back, so after a tap that woke it the bar's buttons ignore taps (`.waking`, `pointer-events: none`) until 400 ms after that finger lifts (2 s at most); a tap that lands on a button still fading out is kept. The bar, badge and screens keep clear of the notch (`env(safe-area-inset-*)`, `viewport-fit=cover`). Full screen, Pop out, Save and 1:1 appear only once the picture plays. States: Waiting, Connecting, Can't connect, Ended (with **Try again**, which reloads), and a Weak signal badge.

**Features.**
- **Share this tab instead.** `getDisplayMedia` asks for `surfaceSwitching: 'include'`, `selfBrowserSurface: 'exclude'`, `preferCurrentTab: false`, `systemAudio: 'include'` and `monitorTypeSurfaces: 'include'`. Chrome then swaps the source on the same track, so viewers and the recording carry on; Porthole's own tab is not offered. Other browsers ignore the keys.
- **Refusal note.** The hub keeps the last 5 refused viewers from the last 10 minutes (time, device label, reason); `/api/info` returns them as `refusals` and the sharer page shows the newest as one line ("An Android phone couldn't join: too many tabs (14:05)").
- **`--verbose`.** Logs each request to stderr: time, client address, method, path and status. The room code (anywhere in the path) and the `room` and `client` query values are replaced by `****`. Off by default, and silent when there is no console.
- **Pause.** Every viewer's video sender switches (`replaceTrack`) to a canvas track showing a plain "Paused" card (dark, centred text, 1280×720, about 2 frames a second) and the shared audio tracks are disabled. Devices that connect while paused get the card too, and Change while paused keeps it. Resume puts the real track back. Since 26 Nov 2026 viewers are told as well and show a small "Paused" note over the picture (see the end). **A running recording is paused with `MediaRecorder.pause()` and resumed with `resume()`, so the paused part is left out of the file** (the file is shorter than the time it covers, and the card never appears in it); the recording length shown on the page leaves the paused time out as well.
- **Pop out** uses `video.requestPictureInPicture()` where `document.pictureInPictureEnabled`, or Safari's `webkitSetPresentationMode('picture-in-picture')`; the button is hidden when neither exists.
- **1:1** zooms so one video pixel covers one device pixel: `videoWidth / (fit width × devicePixelRatio)`, kept between 1 and the 5× maximum (`actualSizeScale` in `web/zoom.js`), around the centre of the current view. Pressed again, it fits. Hidden when that scale would be 1.

# Version 4, P5a: Linux packages and the app window

These replace the matching points above.

- **App window.** Started without `--no-browser`, Porthole opens the sharer page in its own window: the first of Chrome, Chromium, Edge or Brave it finds (`porthole/appwindow.py`) runs with `--app=<sharer page>?window`, its own profile (`~/.config/porthole/browser`; `%LOCALAPPDATA%\Porthole\browser`, machine-local like Chrome's own profiles, so a roaming profile doesn't copy it around; `~/Library/Application Support/Porthole/browser`; a snap-packaged Chromium keeps it in `~/snap/chromium/common`), `--window-size=960,860` and, on Linux, `--class=Porthole` to match `StartupWMClass`. The own profile makes it a separate browser process, so its exit means the window closed: Porthole then stops the way Quit does (`hub.end()`, a short pause, `server.shutdown()`). Without such a browser, or with `--browser-tab`, the page opens in a tab of the default browser as before.
- **A browser that exits within 5 s** handed the page to this profile's browser that was already running, couldn't start, or its window was closed at once. On Linux and macOS Porthole reads the profile's `SingletonLock` link (`<host name>-<process id>`): if it names another process that still runs on this PC, that browser took the page, and Porthole stops when that process exits, that is, when its last window closes. Otherwise an exit with an error opens the page in a browser tab (no tie: Quit stops it), and a clean exit means the window was closed, so Porthole stops; after a clean exit it looks for a lock for up to 2 s first, in case a launcher script started the browser and left. Windows has no such lock: there a clean early exit keeps Porthole running (Quit stops it) and an error opens a tab.
- **The page in the app window** (`?window`) offers, before sharing, "To share a browser tab or its sound, open Porthole in your browser." with **Open in my browser**: the own profile can't see the browser's tabs, so neither a tab nor (on Linux) any sound can be shared there. The button calls `POST /api/open-in-browser` (local, same origin), which opens the sharer page in a tab of the default browser (`xdg-open` in a sandbox) and unties the app window, so closing it no longer stops Porthole; the page then lets go of sharing and closes its window. Its no-sound note points to the same button (on Windows, where the system's sound works in the window, to "Also share system audio" instead). When Porthole stops (Quit, Ctrl+C), the page closes its own window; in a browser tab it stays with the note. The page's words fit a window and a tab alike ("Sharing is on in another window or tab." or "Porthole is open in another window or tab." with **Use this one**, "You can close this page."). The browser tab takes this run's approvals and switches from Porthole (since 24 Nov 2026: see the end).
- **Already running.** The page opens the same way (window or tab), but the running copy's lifetime is never tied to the new window. Run as an AppImage, the place reported by `/api/ping` is the AppImage file (`$APPIMAGE`), since its mount folder changes every run. Programs started from another AppImage inherit its `$APPIMAGE` and `$APPDIR`, so Porthole counts as an AppImage only when its own files are inside `$APPDIR` (`sandbox.appimage()`); the same check decides what `--install-launcher` writes.
- **Sandboxes** (`porthole/sandbox.py`). Snap: `$SNAP` and `$SNAP_NAME`; Flatpak: `$FLATPAK_ID` or `/.flatpak-info`. Inside one, the page opens with `xdg-open` (a strict snap can't start the PC's browsers as an app window, and `webbrowser` fails silently in a Flatpak), and `--install-launcher` says Porthole is already in the app menu.
- **Recordings folder.** `XDG_VIDEOS_DIR` from `user-dirs.dirs` in the real home (`$SNAP_REAL_HOME` in a snap), then `xdg-user-dir VIDEOS` outside a sandbox, then `~/Videos`; plus `Screen shares`. A folder that can't be checked (no permission) counts as missing: Python 3.13 and older raise there, and this runs at every start.
- **No terminal.** The AppImage's start script adds `--launcher` when neither its input nor its output is a terminal (a double-click in the file manager), so start-up problems show as a desktop notification there too; output piped from a terminal (`--help | less`) stays in the terminal. The .deb's `/usr/bin/porthole` runs `/usr/bin/python3`, the Python the package depends on, not whichever `python3` comes first on PATH (pyenv, conda).
- **Notices in the snap.** Inside a snap, libnotify sends `notify-send`'s notices through the desktop portal, which looks the app up by its snap ID; on a real Ubuntu (23 Nov 2026) it answered "The app by ID porthole_porthole could not be found" and nothing showed. Porthole runs `notify-send` there with `NOTIFY_IGNORE_PORTAL=1`, so libnotify talks to the notification service directly, as outside a snap; the snap's `desktop` plug allows that. Still to see on a real PC (`docs/manual-tests.md`).
- **Packages.** A .deb built with plain `dpkg-deb` (app in `/usr/share/porthole`, `/usr/bin/porthole` wrapper), a strict core24 snap, an AppImage built with python-appimage, and a signed APT repository script. CI (`.github/workflows/linux.yml`) runs the tests, builds all three, starts each one, checks it answers `/api/ping` and quits on `POST /api/quit`, and keeps them as build artifacts; a pull request into main gets the tests only, text-only ones too, since main's branch protection requires them. Each carries the licence (GNU AGPL-3.0): the .deb's `copyright` file ends with the full text of `LICENSE`, made at build time as DEP-5 text (`packaging/deb/dep5_text.sh`), the AppImage has `LICENSE` next to `AppRun`, the snap `usr/share/doc/porthole/LICENSE`; CI checks each. The AppImage's Python (python-appimage's manylinux2014 build) brings libraries Porthole never uses, GNU Readline and GDBM (GPL-3.0) among them, so `build.sh` unpacks python-appimage's AppImage, takes those out with the Python modules that load them (`packaging/appimage/trim.py`, which fails the build if anything that stays still needs one) and packs it again with python-appimage's appimagetool; what stays (Python, OpenSSL 3, libffi, bzip2, xz) is listed with its licence texts in `THIRD-PARTY-NOTICES.txt` next to `LICENSE`, with python-appimage's own files and the AppImage runtime appimagetool puts at the start of the file (libfuse, LGPL-2.1, among what it has linked in), and CI checks both, the runtime by its `--appimage-version` (since 26 Nov 2026). The snap's grade is `stable`, which the Snap Store needs for its stable channel. The menu icon is the ring (see Logo above). The menu icon of the .deb and the AppImage is named by the app ID (`io.github.bahrambakhtiyar.Porthole`), not `porthole`: icon themes are searched before an app's own icons, and some (WhiteSur, for one) have an icon called `porthole` for an old package manager of that name, which showed a software-installer icon in the menu (found on a real Ubuntu, 23 Nov 2026). The snap's entry names its icon file by path, so no theme can take its place.

# Start-up: a busy port (23 Nov 2026)

Asked for after a real test on Ubuntu (23 Nov 2026): when the port is in use, Porthole should stop the other copy if it can, and otherwise start on a new port. The snap had been removed while it ran: its process lost network access but kept port 8765, spun at 100% CPU (accept() kept failing and Python's server loop tried again at once) and never answered. The AppImage then said "Port 8765 is already in use. Try: python3 start.py --port 8766", the wrong command for an AppImage. These replace the "Already running" points above.

- **The default port.** `--port` has no default in the parser (None), so Porthole knows whether a port was asked for. Without one it tries 8765 (`DEFAULT_PORT`). When that is taken (in use, or refused as forbidden: Windows can refuse a port another program holds with `SO_EXCLUSIVEADDRUSE`, as Porthole holds its own), it asks `/api/ping` there, waiting at most 2 s (`PING_SECONDS`):
  - **The same copy** (`same_folder`): its sharer page opens and this one ends, as before, so a second click on the menu entry never ends a running share.
  - **Another copy** (another install: the .deb, the snap, an AppImage, another folder): it is asked to quit the way its own page's **Quit** does, `POST /api/quit` from 127.0.0.1 with `Origin: http://127.0.0.1:<port>`. The guard on `/api/quit` is unchanged (a local client, that same-origin `Origin`, and no cross-site `Sec-Fetch-Site`), so a web page from another site and other devices still can't do it; only a program on this PC can. If it says yes (204), Porthole tries the port again every 0.1 s for up to 5 s (`QUIT_WAIT_SECONDS`) and starts there: "Stopped the Porthole from <folder> and started this one." From a launcher this also shows on screen, from its own thread, so a message box waiting for OK never holds up the start. While it waits it asks the port again, so when two starts of the same copy ask together (a double click), the one that loses the port opens the winner's page instead of moving to a spare port.
  - **Anything else** (not Porthole, no answer within the ping's wait, a refused quit, a port still taken after the wait, a reserved port): the next free port, 8766 to 8785 (`SPARE_PORTS`) in turn, then any free port (port 0). The terminal says why: "Port 8765 is busy, so Porthole uses port 8766.", "Port 8765 can't be used here, so ...", "Couldn't stop the Porthole from <folder>, so this one uses port 8766." or "Stopped the Porthole from <folder>, but port 8765 is still busy, so this one uses port 8766." (the last one also on screen from a launcher, since another copy was stopped). A spare port in use is asked too: if it is this copy (moved there by an earlier start), its page opens instead of a second copy starting. That holds once 8765 is free again as well: when 8765 binds, the spare ports something listens on (found by a quick bind) are asked before the new server is used. Reserved spare ports are skipped without asking: Windows reserves whole ranges, and a refused connection to this PC takes a second or two there.
  - Everything uses the port actually used: the viewer links and their QR code (built from the same function), the easy address (`discovery.port`), the port 80 helper's redirect, the firewall line (`sudo ufw allow <port>/tcp`) and the sharer page that opens. Known effect: the sharer page keeps its theme and switches in the browser's storage, which belongs to one address and port, so on another port they start from the defaults; a viewer's home-screen shortcut points at the port it was added on.
  - Other errors at the default port ("Couldn't start: ...") stop as before.
- **An explicit `--port`** never moves and never stops another Porthole: a Porthole already there is opened (named when it runs from another folder), and a taken or forbidden port is the same clear error as before. Its hint names the command for how Porthole was started (`run_hint`): the program when frozen; the AppImage's own file (`$APPIMAGE`, counted only as `sandbox.appimage()` allows, quoted when needed); `porthole` for the .deb and the snap, whose start scripts (`/usr/bin/porthole`, `snap/local/porthole`) set `PORTHOLE_COMMAND=porthole`; else `python3 start.py` (`py start.py` on Windows). Porthole takes `PORTHOLE_COMMAND` out of its environment at start, so programs it starts (the browser, a file manager) don't pass it on to a copy run from source. For port 65535 the hint suggests 65534.
- **A server that can't take connections any more.** The listening socket stays readable while accept() fails, so `socketserver` used to try again at once. `LanServer.get_request` now hands each failure to an `AcceptGuard`: it pauses 10 ms, doubling after each failure in a row up to 0.5 s (failures more than 1 s apart, with nothing waiting in between, aren't in a row), and once failures have gone on without a break for 5 s (`ACCEPT_STOP_SECONDS`) it raises `AcceptFailed`. That isn't an `OSError`, so it ends `serve_forever`; Porthole then tells viewers it ended, closes the port and the easy address, and says "Porthole can't accept connections any more, so it stopped." (exit code 1; from a launcher also on screen, after the port is free). Errors about one connection that was dropped from the queue (`ECONNABORTED`, `ECONNRESET`, `EPROTO`, the network errors accept(2) lists, Windows' `WSAEINTR`) and running short of file handles or memory (`EMFILE`, `ENFILE`, `ENOBUFS`, `ENOMEM` and Windows' equivalents) pause too but never stop it, so neither a phone giving up nor a device holding many connections open can stop Porthole that way; it serves again once they close. The port 80 helper, which runs the same server class, lets go of port 80 quietly, and the page goes back to the address with the port.
- **Tests** (`tests/test_startup.py`, and `AcceptGuardTest` and `AcceptStopsServerTest` in `tests/test_webserver.py`): every branch with a fake binder (no sockets; 8765 is only a number there), then with real sockets on ports the system picks: a second Porthole really stopped, a stand-in that refuses to quit or never lets go, a listener that never answers, a web server that isn't Porthole, the guard still refusing other origins and other devices, and `/api/info` on the moved port. The back-off runs with a fake clock and with a real server whose accept() always fails. The start scripts are run with a stand-in `python3` (`tests/test_packaging.py`).

# Version 4, P5b and P5c: Windows and macOS

These replace the matching points above.

The Windows program and installer and the Mac app and disk image, with their CI, tests and design notes, are parked on the `archive/windows-macos` branch of the private repository since 23 Nov 2026 (Linux comes first; the project's plan, kept private, says how to bring them back). What stays here is how Porthole behaves on Windows and macOS, run from source, and the frozen-app support those builds use.

- **Frozen app.** `porthole/paths.py` finds `web/` and the icons in `sys._MEIPASS` when frozen, else in the folder with `start.py`. Frozen, "already running from <folder>" names the program's folder (on a Mac, the folder that holds `Porthole.app`), hints name the program (`Try: Porthole.exe --port 8766`; on a Mac `Try: open -a Porthole --args --port 8766`), and `--install-launcher` points the Windows shortcuts at the program with `--launcher`. `tests/test_frozen.py` runs Porthole frozen both ways, end to end.
- **No console.** A windowed program (and `pythonw`) has no `sys.stdout` or `sys.stderr`. Porthole then behaves as with `--launcher`: start-up problems, bad arguments and `--help` show in a message box (brought to the front), and `--install-launcher` says what it did in one. Output never stops Porthole: it goes through `say()`, which ignores a missing or broken console, and characters the console can't show (cp1252 has no "ə") print as "?". PowerShell runs without a console window.
- **Windows details.** Recordings go to the Videos known folder (it follows a folder moved to OneDrive or another drive), else `~\Videos`. A PC name that a name lookup refuses no longer stops the address search. Port 5353 held by the system (the DNS client can keep it for itself) leaves the easy address "not available", never a crash. The app window keeps its Windows rule: with no lock link to read, a quick clean exit keeps Porthole running (Quit stops it). Browsers are looked for in `ProgramW6432` first (when set), then `PROGRAMFILES`, `PROGRAMFILES(X86)` and `LOCALAPPDATA`, each folder once, Chrome before Edge before Brave: a 32-bit Python on 64-bit Windows sees Program Files (x86) as `PROGRAMFILES`, and 64-bit Chrome and Brave live in the real Program Files.
- **Windows addresses** (changed 23 Nov 2026). The viewer links come from the adapters themselves (`GetAdaptersAddresses` in iphlpapi through ctypes: IPv4, skipping anycast, multicast and DNS servers, with gateways; a bigger buffer when asked, three tries). Adapters that are up and neither loopback (type 24) nor a tunnel (type 131) give (name, address) pairs, the name being the adapter's own name and its description, so the ranking skips, on Windows only, those whose names say vEthernet or Hyper-V Virtual Ethernet (WSL, Docker, the Default Switch), WSL, VirtualBox, VMware, loopback (Npcap), TAP-Windows, OpenVPN, Wintun, WireGuard, Tailscale, ZeroTier or Bluetooth. One exception: a vEthernet adapter with a gateway is Hyper-V's external switch, which carries the PC's own address, so it stays. Addresses on adapters with a real gateway (not 0.0.0.0) come before the others; the default-route address still goes first when it survives. The PC's mobile hotspot adapter (Wi-Fi Direct) stays, since phones on it can reach the PC. If the adapters can't be read (no iphlpapi, an error code, a record shorter than expected) or none is usable, the older way is used: the PC's name and the default-route address. The record parsing is tested on Linux by a stand-in that lays real records out in the buffer; the real call is tested only when the suite runs on Windows, by hand for now (Windows CI is parked with the builds; the Windows check in `docs/manual-tests.md` covers it too).
- **Windows checkouts.** `.gitattributes` keeps LF line endings in Windows checkouts too (bash scripts fail with CRLF, and some tests compare files byte for byte).
- **No terminal (frozen, Mac).** A frozen Porthole opened from Finder has its output going to `/dev/null`, not nowhere, so the Windows "no console" check doesn't catch it: frozen on macOS, Porthole behaves as with `--launcher`. Start-up problems, bad arguments and `--help` show in an alert: `osascript` with `display alert`, critical for errors and informational for notices, brought to the front, gone after 5 minutes unanswered. The title and the text are arguments read with `on run argv`, never pasted into the script, and the title comes first so a text starting with a dash can't be read as an option.
- **The app window on a Mac.** Chrome and its relatives keep running after their last window closes on a Mac, so the browser's exit can't say the window closed. When Porthole started the app window itself (its own profile), it watches the sharer page instead, through the hub's sharer tracking (the event stream): once a sharer page has connected, no sharer page for 5 seconds (`PAGE_GONE_SECONDS`; a reload is back within a second or two) means the window closed, and no sharer page within 60 seconds of opening (`PAGE_FIRST_SECONDS`) means it never showed. Porthole then stops as when the window closes on Linux, and ends the browser it started (terminate, then kill after 3 seconds; that process only, by its handle, never by name) if nothing else is open in it (next point). A browser of Porthole's profile left from an earlier run that took the page (its `SingletonLock` names it; Chrome writes that lock on a Mac too) isn't ended, only no longer waited for. When Porthole stops for any other reason (Quit, Ctrl+C), it ends the browser it started as well, by the same rule, since on a Mac it would stay behind without windows. With a browser tab (`--browser-tab`, the fallback) Porthole has started no browser and ends none; Quit stops it. Linux and Windows keep the browser's exit. A window whose share moved to a browser tab lets go of the watch (`POST /api/release-window`). Known gap: while the window shows "Sharing is on in another window or tab", or "Sharing moved" after another Porthole window took over (it has no connection then), closing the page that shares counts as the window having gone too (a waiting window takes the free slot only once it has stayed free for 4 s, so the page watch usually decides first).
- **Only when nothing else is open (Mac).** macOS keeps track of running apps by their bundle ID, so the Chrome that Porthole starts counts as the running Chrome. When the person's own Chrome isn't open, a click on Chrome in the Dock, a link from another app, or **Open in my browser** (`webbrowser.open`) can land in Porthole's copy, in Porthole's profile; ending that copy would close those windows too. So before ending it, Porthole asks the browser which pages it shows (`Target.getTargets` over Chrome's DevTools protocol): any page other than the app window's own `/share?window` (a new tab, a site, the sharer page in a tab), or no answer within 2 seconds (`DEVTOOLS_SECONDS`), leaves the browser running. The check runs when the page has gone and when Porthole stops, also after **Open in my browser**: a copy left without windows is ended (it would sit in the Dock and catch the person's own Chrome launches), and a copy holding that tab or the person's pages is left. The question goes over `--remote-debugging-pipe`, two plain pipes and no network port, so nothing else on the computer can reach it. Chrome reads that pipe as fd 3 and answers on fd 4, so on a Mac Porthole starts the browser through `/bin/sh -c 'exec "$0" "$@" 3<&0 4>&1 5>&2 0</dev/null 1>/dev/null 2>/dev/null'` (`DEVTOOLS_SHELL`), with the pipe ends handed over as fds 0, 1 and 2. Chrome quits at once when fd 3 reaches end-of-file, which would happen whenever Porthole stops, so the browser also keeps its own copy of the sending end as fd 5: a browser left running outlives Porthole (the tests check this with real headless Chrome). If the pipes can't be made, the browser starts without them and Porthole never ends it. When Porthole itself ends the browser as it stops, or after **Open in my browser**, a quick exit of that browser is not taken for a failed start, so no fallback tab opens (before, Quit within 5 seconds of opening could open one). This check is in the code shared by every system, so it holds on Linux and Windows too. Known gap: when the person's own Chrome isn't open, **Open in my browser** may open its tab in Porthole's copy, whose profile has none of the person's tabs or sign-ins; to check on a real Mac.
- **Mac details.** Recordings go to `~/Movies/Screen shares`. `--install-launcher` and `--uninstall-launcher` say there is no launcher on a Mac: frozen, that the app goes in the Applications folder; from source, to start Porthole with `python3 start.py`. Addresses come from the interfaces themselves (the same ioctl as on Linux, with the Mac's request numbers), so the Mac's own `.local` name is never looked up, which macOS 15 allows only with Local Network access; if nothing comes back, the name lookup and the default route are used as before. Event streams' keep-alive uses `TCP_KEEPALIVE`, the Mac's name for the quiet time before the first probe, so a vanished phone still leaves within about half a minute. The firewall line says to click Allow if macOS asks whether Python (Porthole, when frozen) may accept incoming connections. The easy address shares UDP 5353 with `mDNSResponder` (`SO_REUSEPORT`); a refused bind, join or send (macOS 15 refuses multicast until Local Network access is allowed) leaves it "not available". The port 80 helper binds all addresses, which ordinary users may do since macOS 10.14; a refusal just leaves plain `porthole.local` out. Screen capture itself is the browser's: macOS asks to allow it (or possibly the app that started it: Terminal, say, from source; Porthole when frozen) under Screen & System Audio Recording (called Screen Recording on macOS 14 and older).
- **Tests on a Mac.** The browser tests give Chrome `--use-mock-keychain` (a fresh profile would ask the Keychain) and open the viewer at the loopback address there, since macOS 15's Local Network privacy may stop a CI runner from reaching its own network address.

## Releases

`.github/workflows/release.yml` runs on a `v*` tag. It waits until the Linux workflow has passed for that tag (it finds the run by the tag's commit and name, checking every 30 seconds for up to 80 minutes; a failed check is tried again, and a run still missing after 5 minutes means the workflow never started, so it stops with that error), downloads its build files, checks that exactly the three files are there (the .deb, the AppImage and the snap, each once), and makes one draft release with them. Only this job can write to releases (`contents: write`, plus `actions: read` to download the other run's files); the build workflow stays read-only. A build that fails means no draft: fix it and tag again, or re-run the failed build and then this workflow (a draft left by an earlier attempt gets its files replaced). Two Release runs for one tag run one at a time. On a tag, the Linux workflow also writes the tag's version into `snap/snapcraft.yaml` before building, so the snap matches the other packages. It also checks that the newest `<release>` in the AppStream metainfo is the tag's version (software centres show it as the version), so add one before tagging.

**The Snap Store.** `.github/workflows/snapstore.yml` runs when a release is published: it downloads that release's snap and uploads it to the Snap Store's stable channel with `snapcraft upload --release=stable`. The draft stays the owner's to check, so publishing it is the go for the store too, and nothing reaches the store before a person has looked. Run by hand (Actions, Snap Store, Run workflow) with a tag, it uploads the snap of a release already out. The store login is the repository secret `SNAPCRAFT_STORE_CREDENTIALS`, made with `snapcraft export-login --snaps=porthole`; without it the run stops and says so. The tag goes through an environment variable and must look like `v1.2.3`, so nothing from a release name reaches a shell command.

The release has its own workflow because separate release jobs in each build workflow, sharing one concurrency group per tag, lost files once there were three build workflows: GitHub keeps one running and one pending job per group and cancels the older pending one. The archive branch's copy waits for all three workflows and checks all seven files.

# Accessibility (23 Nov 2026)

The sharer page, the viewer page, the mini controls window and the small message pages were checked against WCAG 2.2 level AA, in light and dark, at desktop and phone sizes. These replace the matching points above.

## How it was checked

- **Colour contrast** is computed, not eyeballed: `tests/test_contrast.py` reads the colour tokens from `web/style.css` for both themes (and checks that Auto's dark block matches Dark), and checks the pairs the stylesheet actually uses; a second test checks those pairings are still in the CSS, and that fixed colours appear only in the viewer's black picture area and the QR code's white square. The viewer's controls float over the picture, so they are checked over a white and a black picture, in every state (plain, hovered, pressed, pressed and hovered, each also focused), with the colours the browser's cascade would pick for that state (`bar_button_style`: most specific matching rule, then the later one), since one rule read alone missed a pressed button under the pointer. Run `python3 tests/test_contrast.py` to print the table.
- **Behaviour** is checked in headless Chrome (`tests/browser/run.mjs`): names, roles and descriptions in Chrome's accessibility tree (`Accessibility.getFullAXTree`, and one element's node for the focused viewer row), real key presses (`Input.dispatchKeyEvent`), where focus lands, what each page's live region is given and how often (also lines that appear later, through answers the test gives in Porthole's place with the DevTools `Fetch` domain, so nothing is announced on the network), the viewer's keys for zooming and moving, a pressed viewer button's colours with hover forced on (`CSS.forcePseudoState`), every visible control at least 24 × 24 px, the sharer page at 600 px and 320 px wide (200% and 400% zoom), and a viewer screen at 320 × 256 (400% of 1280 × 1024, with its own words and with the longest words any viewer screen has), each with and without wider text spacing (line height 1.5, letter spacing 0.12 em, word spacing 0.16 em, paragraph spacing 2 em): no sideways scrolling, nothing cut off. The spacing is added as a style sheet through the DevTools protocol, the way a reader's extension adds it, and the test checks it took effect: the page's security rules (`default-src 'self'`) refuse a `<style>` a script adds, so the first version of this check measured the plain page twice.
- **Markup and CSS** rules are checked in `tests/test_pages.py`; the DOM-free parts (what is announced, where focus goes) in `tests/js`.

## Fixes

- **Viewer focus ring over the picture.** It was drawn 2 px outside the button, so over a light picture it vanished (1:1 on white), and on a pressed button (white) it was white on white. It is now drawn inside the button, on the button's own colour (white on the dark buttons, black on a pressed one), whatever the picture. The "Tap to play" screen's Play button gets a white ring for the same reason.
- **A pressed viewer button under the pointer** (Sound, 1:1) kept its black text and ring but took the dark grey hover background (2.18:1 over a white picture, 1.49:1 over a black one): the hover rule was more specific than the pressed one. A mouse click leaves the pointer over the button it pressed, and phones keep hover on the button last tapped, so this was the usual look right after pressing. The hover rule now leaves pressed buttons alone.
- **"Tap to play"** was a clickable box that no keyboard could press. It now has a **Play** button.
- **Keyboard focus never falls back to the top of the page.** A button that hides or goes away while focused hands focus on: Start sharing to Stop sharing, the sharing controls (and **Use this one**) to Start sharing (`replacementFocus`). After Allow, Deny or Remove, focus goes to the next row in the same list (or the one before), after the last Allow to the allowed row under Watching, and when a list empties (Deny all) to the Watching heading (`focusAfterChange`); never to a button, since a held Enter key would press that too. Rows (`tabindex="-1"`) and the Watching heading take that focus. A focused row reads the device, its code and its state ("Linux PC 2, code 717, Watching": `rowLabel`, as its `aria-label`), not its buttons; its live numbers' tooltip sits on the name part, which never takes focus (on the row itself it was read as the row's description, and again each time the numbers changed, every 2 s). Chrome drops the focus of a disabled button, so **Record**, briefly disabled while a recording starts, gets it back. When the page reconnects and finds another window or tab sharing ("Sharing is on in another window or tab."), focus on a control that is turned off goes to **Use this one**; this is decided as the controls turn off, since Chrome drops their focus only a moment later (the browser test doesn't reach this screen with focus on a control). When another tab takes over with **Use this one**, the old page ends instead: all its buttons are off and its note is read out. A row keeps its focus when a device listed above it leaves: rows of devices that left are taken out before the rest are put in order, because moving the focused row dropped its focus (onto the row, at best). Focus moved after a click or touch (Allow clicked, its row moved to Watching) doesn't scroll the page; after a key it does, so the focus can be seen.
- **Announcements.** A live region that is shown or hidden is often not read out, and one written on every redraw is read out again and again. Each page now has one live region that is always there (`#say`, `role="status"`, visually hidden) and is written only with something new:
  - sharer page: each device that starts waiting, once ("Android phone wants to watch. Code 482.", `waitingNews`), notes as they appear (whole screen shared, no sound, Porthole stopped, sharing moved, sharing on in another window or tab, recording saved, a device turned away; since 26 Nov 2026 the waiting page's line is said by its status line instead: see the end), and lines that appear after the page was drawn: an Easy address error or note (they describe the switch too, but a changed description isn't read out again, and the error comes a moment after the switch was read as on) and "This PC has no network" (`lineNews`: what comes with the page is read with the page). The status line keeps its own polite region; errors stay an alert and are written only when they change. The region is cleared and the news written 100 ms later (`newsWriter`): a live region given the words it already holds says nothing, so a note that came back with nothing said in between (the whole-screen note after Stop and Start) used to be silent. News given within those 100 ms is said together;
  - viewer page: the screen's words in short sentences, with the check code while waiting ("Waiting. Ask the sharer to let you in. Your code: 482"), then Watching or Weak signal while the picture plays (`spokenState`). The overlay and the badge are no longer live regions, so nothing is said twice;
  - the mini window says new waiting devices too (it may have the focus).
- **Names and roles.** The switches are named by their label only and described by their line (`aria-labelledby`, `aria-describedby`); Easy address is also described by its error or note, which explains a greyed-out switch. The QR code is one image, "QR code to open the link on a phone" (the picture inside is hidden), so the link is read once, as text. The viewer's picture is "Shared screen" (Chrome called it "Unable to play media."). The viewer's bar is a named group, not a toolbar, which would promise moving between its buttons with the arrow keys (they move the picture instead, below). The mini window's Allow and Deny name the device ("Allow Android phone").
- **Viewer idle bar and keys.** Tab while the bar is hidden brings it back and lands on a control that can be seen (hidden controls can't take focus). The bar stays while focus moved by a key or by a screen reader is in it; focus left by a touch or click doesn't keep it, and when the bar hides, a focused button in it gives up the focus, so a key press never presses a hidden control (Chrome already does this; other browsers may not). The quality menu keeps keyboard focus after a change (arrow keys change a closed menu at once; it used to drop the focus, stranding keyboard users); after a touch or click it still lets go, so the bar can hide. When the share ends while focus is in the bar, it moves to **Try again**. A focused bar button that hides itself (**Fit** once the picture fits, the picture's buttons when it stops) hands the focus to the nearest control still shown (Fit to 1:1), not to the top of the page. **Zoom by keyboard:** **+** (or **=**) and **-** zoom around the middle of the window, and while zoomed the arrow keys move the picture a tenth of the window, as scrolling would (`viewForKey` in `web/zoom.js`), so the whole of a 1:1 picture can be read; before, zooming and moving needed a pointer, and 1:1 by keyboard only ever showed the middle. Not while the quality menu has the focus (its arrow keys change the quality), not with Ctrl, Cmd or Alt (the browser's own zoom), and only while the picture shows.
- **Landmarks, headings, titles.** The viewer page has a `main` landmark and its screen title is a heading. Titles say where you are: plain "Porthole" on the sharer page, which names the app window and its tab (since 23 Nov 2026; the waiting count goes in front: "(2) Porthole"), "Shared screen · Porthole", "Mini controls · Porthole", and "<message> · Porthole" on the message pages. An iPhone home-screen shortcut is still named Porthole (`apple-mobile-web-app-title`).
- **Target size.** "Other addresses" was 21 px tall; it is 24 px now. Everything else was already at least 24 × 24 px (row buttons 34 px tall, viewer buttons 40 px, the switch 44 × 24 inside a row-wide label).
- **"Nothing shared yet".** It reloaded itself every 5 seconds, so screen readers read the page out again each time. A small script (`web/retry-page.js`) now checks quietly every 5 seconds and goes on only when the answer changes (to the share, or to "Nothing here" once the easy address is off); browsers without scripts still reload (`<noscript>` refresh).

Already fine and kept: `lang="en"` everywhere, one `h1` and section `h2`s on the sharer page, every control reachable by keyboard in reading order (the theme switch is one stop with arrow keys), visible focus rings in both themes, `prefers-reduced-motion` turning off the spinner and every transition (a test now checks every transition and animation has its reduced-motion rule), nothing that flashes, no orientation lock, and the one-column layout at 200% and 400% zoom. The viewer page keeps pinch for zooming the picture rather than the page; the browser's own text size and zoom settings still enlarge its words.

## Left for a real screen reader

None of this was tried with a real screen reader here; `docs/manual-tests.md` lists the checks. Most likely to need work:

- **VoiceOver on iPhone and TalkBack on Android:** the viewer's bar hides after 3 seconds, and hidden controls are out of the screen reader's reach too. A double tap on the picture should bring it back; whether it stays while the screen reader's cursor is on a button depends on whether the phone moves the page's focus with that cursor (the bar stays while focus is in it). If not, the bar may hide under the cursor; how to keep it shown then (pages can't tell that a screen reader is on) is still to be decided.
- **NVDA on Windows (Chrome, Edge, Firefox), Orca on Linux, VoiceOver on a Mac:** that a new waiting device is read once, notes and errors are read (also a note read again after Stop and Start, and an Easy address error that comes after the switch), and focus after Allow, Deny, Deny all, Start sharing and Stop sharing reads sensibly (a focused row reads its name, code and state, and stays quiet while its live numbers change). Copy's "Copied" is the button's own text: NVDA, JAWS and Orca read a name change on the focused button; whether VoiceOver on a Mac does is to check (if not, it could also go to the live region, at the cost of being read twice elsewhere).
- The mini window's announcements while the main page is in the background, and whether each screen reader reads a polite region in a window that doesn't have the focus.

# Refinements (23 Nov 2026)

Found by reviewing the whole app; each fix has a test.

- **Stopping.** The server runs on a thread of its own and the main thread only waits, so Ctrl+C interrupts the wait and the server keeps taking connections while the pages finish: the sharer page hears "ended", sends a recording's last piece and closes it (Porthole waits 0.5 s, and up to 3 s while a recording is open; a second Ctrl+C skips the wait). Before, the server stopped at once and the page said the recording failed. SIGTERM (`kill`, logging out) and SIGHUP (the terminal window closed) take the same path; a signal set to be ignored (`nohup`) stays ignored. Before, both ended Porthole at once: viewers kept retrying, the easy address stayed, and the app window kept sharing. After Quit, or another Porthole asking this one to quit, the terminal says "Stopped."; the app window closing right after a Quit no longer says "Window closed. Stopped." instead.
- **`--no-browser` with a copy already running** says where it is ("Already running: http://127.0.0.1:8765/share") instead of claiming it opened the page.
- **The .deb** runs `/usr/bin/python3`, and `--install-launcher` there says it is already in the app menu instead of adding a second entry that hid the package's. (Since 24 Nov 2026 it also removes an older entry that hides the package's: see the end.) The AppImage takes `--launcher` only when neither its input nor its output is a terminal.
- **A quiet terminal.** A connection dropped mid-request or a reply the browser gave up on (any `OSError` in a handler) prints nothing; other errors still print their traceback. A request line whose address can't be read (`GET http://[::1/x`) gets a plain 400 instead of no reply and a traceback.
- **"Use this one".** The page in Porthole's own window that is taken over by a browser tab calls `POST /api/release-window` (local, same origin), which unties the window as **Open in my browser** does, so closing it, as its note invites, no longer stops Porthole and ends the new share. Only a browser tab taking over unties it: another Porthole window shares the same browser (its event stream says `window=1`, and `replaced` passes that on), so the tie stays and closing the last window still stops Porthole. The page taking over reads the approvals and switches again first: the other tab may have allowed, denied or removed devices, or turned Easy address off, while it waited (since 24 Nov 2026 from Porthole's copy, which also reaches a page in another browser: see the end).
- **Small page fixes.** A browser without screen capture keeps "This browser can't share the screen" and Start sharing stays off after connecting. Quit no longer says "Porthole has stopped" twice when "ended" arrives first. A viewer whose picture still needed "Tap to play" gets it back when the link returns after a blip, instead of a still frame with nothing to tap.

# Refinements, second round (24 Nov 2026)

- **The waiting page** ("Sharing is on in another window or tab", or "Porthole is open in another window or tab" while the other page doesn't share, since 24 Nov 2026) has no viewers of its own. Its Quit asks first when the other page shares (`sharing` in `/api/info`). Easy address and **Open in my browser** stay off with the other controls; before, the switch came back on with each redraw, and the button untied the window that was sharing. It has no event stream to hear "ended", so it notices by itself that Porthole has stopped (no answer from `/api/info` twice, a second apart, or a new room) and ends like any page, closing Porthole's own window. Once a page has let go, its title no longer counts waiting devices.
- **A page that connects while Porthole is stopping** hears "ended" right after its hello, instead of retrying for ever once Porthole has gone.
- **An event stream that can't start** (out of file handles) leaves no peer behind; before, the page stayed "connected" for good.
- **The viewer.** A picture the browser pauses by itself (picture-in-picture closed, headphones gone, a media key) shows "Tap to play" instead of a still frame. Fit shows only over a picture, and a share that ends takes its zoom with it. The page says whether the device has a touch screen (`touch=1`): an iPad's browser says Mac, so a Mac with a touch screen is listed as an iPad.
- **`--help` and argument errors** name the command people type (`porthole`, the AppImage file), not `start.py`.

# Refinements, third round (24 Nov 2026)

- **Porthole's own window** is tied again when a page in it shares again after a browser tab had taken over (a sharer stream with `window=1` calls `AppWindow.retie()`), so closing it stops Porthole again. Starting the same copy again waits until the new window has started (`AppWindow.settle()`, a few seconds at most), so a browser that can't start still falls back to a tab before this copy ends.
- **A second sharer page** turns its controls off as soon as it sees another page sharing, while it waits up to 3 s for that page to let go, and its Quit asks then too. Quit asks only when it would cut something live: someone watching what is shared, or a recording. A page doesn't report sharing before it is the sharer.
- **A page from an earlier run** (Porthole killed and started again on the same port) ends once its stream is refused (since 26 Nov 2026 saying Porthole was restarted when the new run answers: see the end). Its actions carry its room (`X-Porthole-Room`), which the server checks, so it can't stop or change the new run.
- **Ctrl+C pressed again** once the wait is over does nothing (`_Stopper` in `app.py`, one handler for Ctrl+C, SIGTERM and SIGHUP through serving, the wait and the rest of the stop): no traceback, and the easy address's goodbye and the recording's close still happen. "Press Ctrl+C" is printed once Ctrl+C is handled that way.
- **Odd messages:** a `quality` mode or `waiting` reason that isn't a string gets a 400. **Device names:** Android tablets and Chromebooks are named as such.

# Refinements, fourth round (24 Nov 2026)

- **Tying the window again** also works when it opened in a browser already running with Porthole's profile (one left from an earlier run): Porthole still watches that browser, so `retie()` only gives up once nothing watches the window any more.
- **Ctrl+C before serving** (while start-up asks a program on the port, or "Already running" waits to see its window start) ends quietly: "Stopped.", or nothing after "Already running".
- **A page from an earlier run** in Porthole's own window closes as with every other ending; its browser would otherwise keep the new run's window from being followed. After "Moved", **Open folder** still works for a recording just saved.
- **"Nothing shared yet"** waits through a 404 or two in a row: the easy address is off for a moment while Porthole starts and when the PC's address changes.
- **The terminal** says the network address changed only when the main link did, not when another address comes or goes (and since 26 Nov 2026 not when the network comes back with the same link: see the end). The mini window names the check code ("Code 482"); **Full screen** and **Pop out** say when they are on (`aria-pressed`), as Sound and 1:1 do.

# Refinements, fifth round (24 Nov 2026)

- **Ctrl+C right after "Press Ctrl+C"** no longer leaves Porthole stuck: `serving` is set only once the server's thread has started, so a stop never waits for a thread that never began (later signals were ignored by then). Ctrl+C during start-up's port check prints "Stopped." on a line of its own.
- **The waiting page** takes the free slot when the page that shared has closed, so a device waiting to be let in has someone to let it in. **A page that let go** (Stopped, Moved) lists no devices.
- **Try again** on a viewer's last screen shows Connecting and reloads once Porthole answers; a reload while it was still down showed the browser's own error page, a dead end in a home-screen app.

# Visible changes (24 Nov 2026)

Eleven visible changes were agreed on 24 Nov 2026. All eleven are built; they replace the matching points above.

- **A recording with nothing in it.** A recording started while paused and stopped before Resume has no picture (MediaRecorder is paused straight after it starts, so at most a file header goes in). The page keeps `recorded` on each recording (true unless it started paused, and set by Resume) and stops it with `/api/recording/stop?recorded=0` when no picture went in. Porthole deletes such a file, and any file with no pieces at all, and answers `{"empty": true}`; the page says "Nothing was recorded." on the Saved line's place, with no Open folder, and announces it (`recordingOutcome` in `web/share-helpers.js`). A recording closed with no pieces because its page went away, Porthole quit or a new one started is deleted too (it used to stay as an empty file); one with pieces is kept as before. **Change** while paused continues the recording in a new file that has no picture until Resume: stopped before Resume, that file goes too, and the page shows the part before Change again (its Saved line and Open folder, said again), not "Nothing was recorded." (`keptRecording`; the new recording remembers what the one before it saved).
- **A recording cut short by a write error.** Recordings are written unbuffered (`open(..., buffering=0)`), so a write that fails fails at once, never again later when the file is closed, and the file holds exactly the pieces taken so far; a short write carries on with the rest of the piece. When a write fails (`ENOSPC` for a full disk, which Windows reports too), the half-written piece is cut off again (`truncate` to the last whole piece, which also gives some space back), the file is closed, and that piece and every later one get a 507 with `stopped`, the reason in plain words: "the disk is full" (`ENOSPC`, `EDQUOT`), "the file is too big for this disk" (`EFBIG`: 4 GB on a FAT32 stick), "the disk is read-only" (`EROFS`), "Porthole isn't allowed to write there" (`EACCES`, `EPERM`), else "the disk can't be written to" (`write_reason` in `porthole/recorder.py`). The page then ends the recording as usual: `/api/recording/stop` answers with the file and `stopped`, the Saved line and Open folder show, and the error line says "The recording stopped: the disk is full. What was recorded until then is saved." (before: "Couldn't save the recording: can't write the file: No space left on device", and no Saved line). If nothing had been saved yet, the file is deleted and the page says "The recording stopped: the disk is full." and "Nothing was recorded."
- **Another name for the PC.** A page opened by a name the Host check refuses (the PC's own `mypc.local`, a router's name for it, any name but the easy address) gets the message page "Use the link · Open the link or scan the QR code shown on the sharing PC." instead of "Bad request · Open this page by its IP address.", from the main server and the port 80 helper alike. Only the words changed: the same requests are refused (status 400), since a page loaded by a name a stranger controls could point at this PC (DNS rebinding); requests from pages (`POST`) still get `{"error": "bad host"}`. The one exception is the message pages' style sheet, `GET /static/style.css`, served whatever the Host (by the port 80 helper too): the page asks for it by the same refused name, and refused, it came back as the 400 page, so the message showed unstyled. It is a public file, so a page by a stranger's name gains nothing.
- **An older menu entry under the .deb's.** `--install-launcher` from the AppImage or a folder writes `~/.local/share/applications/porthole.desktop`, the same desktop ID as the .deb's `/usr/share/applications/porthole.desktop`, so it comes first in the menu and hides the package's. Run as the .deb (`PORTHOLE_COMMAND` set, no sandbox), `--install-launcher` and `--uninstall-launcher` both remove such an entry (`launcher.remove_older_entry`), with the AppImage's copy of the icon when that entry used it, and say "Removed an older Porthole menu entry; the package's own entry stays."; with none there they answer as before ("Porthole is already in your app menu.", "Porthole's menu entry comes with the app. Uninstall the app to remove it."). Only the user's folder is looked at, so the package's entry is never touched, and only an entry Porthole wrote goes: a regular file whose `[Desktop Entry]` has `Name=Porthole` and Porthole's own comment ("Share this screen with phones and PCs on the same network"; the package's entry has another), so another app's `porthole.desktop`, a copy of the package's entry or a link to it stays, and an entry Porthole wrote that someone edited (another `Exec`) still counts. `--uninstall-launcher` from a folder or the AppImage follows the same rule. The snap and a Flatpak can't reach the user's menu folder, and their entries have names of their own, so they answer as before.
- **Easy address off stops new visitors only.** Turning Easy address off (which turning Ask off does) used to withdraw `porthole.local` at once: viewers who came by it kept their picture (the video goes by address) but couldn't reconnect or get the next share, since each request looks the name up again. Now the web server tells `Discovery` about each viewer stream that came by the name (`guest_arrived`, `guest_left`, by device address). When it is turned off while such devices are watching, or between two streams (gone less than the wait), the name stays answered for them: `enabled` is false at once (the page shows the switch off, and `/` and old room links send nobody to the room), and the Host check admits the name only from those devices (`Discovery.admits`), so any other device that comes by the name gets "Use the link", whatever it asks for (but the public style sheet, see "Another name for the PC"). The set of devices is fixed when it goes off; nothing is added to it later, and a device the sharer denies or removes leaves it at once, even if its stream stays open (the web server notes the "denied" or "removed" message it relays). Once each of them has had no stream by the name for 2 minutes (`LINGER_SECONDS`, as long as a device may keep the name's answer anyway), the name goes with its goodbye, as before. Turning it on again ends the wait with the same announcer; Porthole quitting or the PC's address changing withdraws the name at once. Why this rather than a warning: the rule behind "Ask off turns Easy off" (nobody new joins by the name without Ask) holds by two locks, so it is airtight: the room code is handed out by the name only through `/` while Easy address is on, and while the name stays, only devices that were already watching by it (and so already have the room) may use it at all. A device that takes over the address of one of them would still need the room code, which is the link itself.
- **Notifications asked for at Start sharing.** Ask is on from the start, and the browser was asked for leave to show "2 waiting" only when Ask was turned on by hand, so with the default switches the notification never showed. Now **Start sharing** asks too, while Ask is on (`askForNotifications` with `askToNotify` in `web/share-helpers.js`): only while the browser has no answer (`Notification.permission` is `default`, so never again after a refusal, and not after a yes), and once per page, so a prompt closed without an answer isn't shown on every Start sharing. Turning Ask on by hand asks by the same rule. The request goes out in the same click, right after the screen picker is opened: Firefox asks only in answer to a click, and the picker, which needs the click too, goes first so sharing never depends on the notification prompt.
- **"No network" comes back by itself.** "This PC has no network. Connect it to Wi-Fi, then restart Porthole." asked for a restart that isn't needed and makes a new link. The line now says "This PC has no network. Connect it to Wi-Fi or a network cable; the link shows here once it's connected." It already came back by itself: the address watcher reads the addresses every 10 seconds (also from none to one, which announces the easy address there if it is on), `/api/info` gives the new link, and the page's 10-second check draws the link and the QR code and hides the line. Tests now pin each step, the browser test included.
- **The waiting page says whether the other page shares.** A page that finds another one is the sharer said "Sharing is on in another window or tab." also when that page was only open. It now says "Porthole is open in another window or tab." then (`busyText`, from `sharing` in `/api/info`, read when it starts waiting), and follows the other page at its 10-second check: a change is said once (`lineNews`; since 26 Nov 2026 by the status line, which says it too, and the page has no Watching list: see the end). Once the other page has gone (closed, or its stream dropped: `sharer_active` false), this page takes the free slot itself (fifth round, above). **Use this one** stays.
- **Porthole keeps this run's approvals and switches.** After **Open in my browser** the page runs in another browser with its own saved settings, so devices already let in waited again, denied ones were asked about again, and the switches went back to the defaults (Easy address on, which could announce the name again). Now the page that shares reports its switches (Ask, Easy address, Smooth motion) and its lists of devices let in and turned away to Porthole at its hello and after each change (`POST /api/choices`, `keepChoices`), and `/api/info` hands them out (`choices`). A page that connects or takes over (**Use this one**, the browser tab after **Open in my browser**, a reload) reads them first and uses them for this run instead of what its own browser saved (`useChoices`, `readChoicesAgain`); only a switch changed on that page is saved in its browser: the change is made to what that browser saved (`saveSettings(change)`, Ask and Easy address together, as they are linked), so the switches taken over aren't saved with it.
